## 1. Pandoc binary bundling on Vercel

**Vercel's own bundle-size limits** ([vercel.com/docs/functions/limitations](https://vercel.com/docs/functions/limitations), last updated 2026-07-01):
- Standard Node.js function: **250 MB uncompressed**, including layers — "enforced by AWS" (Lambda's own limit).
- **Large Functions** (beta): up to **5 GB** uncompressed, but requires Fluid Compute + Active CPU billing enabled, opt-in via the `VERCEL_SUPPORT_LARGE_FUNCTIONS` env var, and is *not* supported alongside Secure Compute or Static IPs.

**Pandoc's own binary**: the latest GitHub release (v3.10.2, confirmed via `github.com/jgm/pandoc/releases/latest` and the GitHub Releases API) ships `pandoc-3.10.2-linux-amd64.tar.gz` at **34,877,720 bytes (~33.3 MB) compressed**. Pandoc's install docs ([pandoc.org/installing.html](https://pandoc.org/installing.html)) describe the Linux binary as "statically linked and has no dynamic dependencies or dependencies on external data files" — i.e. a genuinely self-contained single executable, no shared-library install step. At ~33 MB, this comfortably fits inside Vercel's 250 MB standard bundle cap on its own.

**PDF output requires an external engine.** Pandoc's manual ([pandoc.org/MANUAL.html](https://pandoc.org/MANUAL.html)) is explicit: producing a `.pdf` output "by default... uses LaTeX to create PDFs, which requires a LaTeX engine installation." The `--pdf-engine` flag accepts alternatives: `pdflatex`, `lualatex`, `xelatex`, `latexmk`, `tectonic`, `wkhtmltopdf`, `weasyprint`, `pagedjs-cli`, `prince`, `context`, `groff`, `pdfroff`, `typst`. None of these ship inside the Pandoc binary — every one is a separate install. Pandoc's own install instructions recommend `apt-get install texlive` for the default path, and note LaTeX needs supporting packages (`amsfonts`, `amsmath`, `unicode-math`, `listings`, `graphicx`, `babel`, etc.) "to improve output quality."

**Is bundling a LaTeX engine on top realistic?** No, not for the default TeX Live path — a full TeX Live install runs into multiple gigabytes, far past even the 5 GB Large Functions beta ceiling once you add Pandoc, Node.js, and app code to the same budget, and TeX Live itself isn't distributed as a single portable static binary the way Pandoc is. A curated minimal subset (e.g. TinyTeX-style) could theoretically land in the 200–500 MB range, but that requires bespoke package curation, isn't officially supported by Pandoc, and still consumes most of the standard 250 MB budget or forces reliance on the still-beta Large Functions tier. Lighter engines exist — `typst` compiles to a single static binary in the tens-of-MB range, and `tectonic` is a self-contained LaTeX-workalike — but both are added scope beyond "just Pandoc" and (for `tectonic` specifically) can fetch TeX packages over the network at build time, which is a poor fit for a read-only serverless filesystem. `wkhtmltopdf` is itself a ~80–90 MB WebKit-based binary and the upstream project has been effectively unmaintained/archived for years.

**Pandoc's DOCX writer avoids all of this.** The manual confirms DOCX output is a native writer that emits Office Open XML directly — "no external engine is required... Pandoc generates Word documents directly in Office Open XML format" — and supports styling via `--reference-doc` without any external tool. So the DOCX half of a Pandoc-binary approach is bundle-feasible; the PDF half is not, without pulling in a second large, separately-licensed dependency.

## 2. Pandoc-wasm / WASM builds

The **official** WASM build is maintained by the Pandoc project itself at [github.com/pandoc/pandoc-wasm](https://github.com/pandoc/pandoc-wasm), published to npm as [`pandoc-wasm`](https://www.npmjs.com/package/pandoc-wasm) (npm registry: latest `1.1.0`, published 2026-06-11, **58.6 MB unpacked** — it wraps the compiled `pandoc.wasm` binary directly in the package). Per its README (`raw.githubusercontent.com/pandoc/pandoc-wasm/main/README.md`):
- Supports Node.js 18+ via ES modules and runs in browsers; it "automatically detects the Node.js environment and loads the WASM binary from the filesystem without configuration" — so it is **not** Edge/browser-only, it runs fine inside a standard Node.js serverless function.
- Explicit, documented limitations: **no HTTP requests** (sandbox isolation blocks fetching remote resources), **no external programs** (filters must be Lua, not shelled-out executables), and — critical for this ticket — **no PDF output**: *"Cannot produce PDF directly, as this requires external programs like LaTeX, ConTeXt, or Typst which cannot be executed in the WASM sandbox."* This directly confirms the same LaTeX dependency problem from section 1 applies inside the WASM sandbox too, with no workaround.
- DOCX output is not explicitly called out in the README's limitations list, and since Pandoc's DOCX writer doesn't shell out to anything (section 1), it's plausible pandoc-wasm can still produce DOCX — but this isn't confirmed in the primary source, and at 58.6 MB unpacked for a capability the pure-JS `docx` package (section 3) delivers in 4.65 MB, there's no real advantage even if it works.

Other WASM builds exist but are secondary/community efforts, not first-party: [georgestagg/pandoc-wasm](https://github.com/georgestagg/pandoc-wasm) is a separate, community Asterius-compiled build described in its own materials as "fairly fragile... with room for stability improvement when converting larger documents or including images"; [y-taka-23/wasm-pandoc](https://github.com/y-taka-23/wasm-pandoc) is another, older community build. Neither is a better fit than the official `pandoc/pandoc-wasm` package, and none change the fundamental PDF-via-LaTeX blocker.

**Conclusion: pandoc-wasm rules out PDF entirely**, by its own documentation, and offers no clear size/complexity win over pure-JS alternatives for DOCX.

## 3. JS-native alternatives

**PDF via headless Chrome** (`puppeteer-core` + `@sparticuz/chromium`): Vercel's own knowledge base guide, [Deploying Puppeteer with Next.js on Vercel](https://vercel.com/kb/guide/deploying-puppeteer-with-nextjs-on-vercel), documents and recommends exactly this pattern — `puppeteer-core` ("a lightweight version of Puppeteer that doesn't bundle its own browser") paired with `@sparticuz/chromium` or `@sparticuz/chromium-min` ("small enough to fit within Vercel's limits"), citing Vercel's 250 MB function bundle cap as the reason full `puppeteer` (which downloads its own Chromium) doesn't work. Vercel even ships a ready-made "Puppeteer on Vercel" template pre-configured with these packages.

`@sparticuz/chromium`'s own README ([raw.githubusercontent.com/Sparticuz/chromium/master/README.md](https://github.com/Sparticuz/chromium)) gives concrete numbers:
- Uncompressed Chromium binary: **136,964,856 bytes (~130.6 MiB)**.
- Brotli-compressed (what actually ships in the function bundle): **~33.2 MiB** (level 11, slowest/smallest) to **~38.9 MiB** (level 5, fastest decompression, ~0.6s).
- Recommended memory: **at least 512 MB, 1600 MB+ recommended**.
- The `-min` variant ships *without* the compressed Chromium payload at all — it downloads a pack tarball from a URL you host (e.g. Vercel Blob) on cold start, untars to `/tmp/chromium-pack`, and decompresses to `/tmp/chromium`, trading bundle size for a one-time network fetch per cold container.
- The npm registry's `unpackedSize` for the current release (`149.0.0`) is 69.68 MB, well inside Vercel's 250 MB uncompressed cap even before subtracting for the `-min` variant.
- The README does not mention Vercel by name (AWS Lambda is its documented target), but Vercel's Node.js runtime is Lambda-based, which is why Vercel's own KB guide layers this package on top without issue.

Route: Markdown → HTML via the `unified`/`remark`/`rehype` ecosystem (well-established, pure JS, no bundling concerns of its own), then Chromium's print-to-PDF renders that HTML to PDF.

**Purpose-built PDF packages, checked against their own npm/GitHub metadata:**
- [`md-to-pdf`](https://www.npmjs.com/package/md-to-pdf) (registry: latest `5.2.5`): its own declared dependency list includes **`puppeteer` (full, not `puppeteer-core`)**, `>=8.0.0`. Full `puppeteer` downloads/bundles its own Chromium at install time — the exact problem Vercel's KB guide says to avoid. This package is **not serverless-safe out of the box**; using it on Vercel would require forking or patching it to swap in `puppeteer-core` + `@sparticuz/chromium`, at which point you're just hand-rolling the puppeteer-core approach above with extra indirection.
- [`@react-pdf/renderer`](https://www.npmjs.com/package/@react-pdf/renderer) (registry: latest `4.8.1`): its dependencies are headed by **`pdfkit`**, a pure-JS PDF generation library — confirmed **no headless browser, no external binary**. It works by rendering a tree of its own React components (`View`, `Text`, `Page`, etc.) through a custom reconciler into PDF primitives — it does **not** render arbitrary HTML/CSS. Converting Markdown to a react-pdf document means walking the Markdown AST (e.g. via `unified`/`mdast`) and mapping nodes to react-pdf components yourself, rather than reusing an HTML pipeline. More upfront engineering, but it eliminates the Chromium dependency (and its ~35–130 MB footprint and browser-launch cold start) entirely.

**DOCX via the `docx` npm package** ([npmjs.com/package/docx](https://www.npmjs.com/package/docx), docs at [docx.js.org](https://docx.js.org)): registry data for the current release (`9.7.1`) shows dependencies of `jszip`, `xml-js`, `xml`, `nanoid`, `hash.js`, `@types/node` — **all pure JS/TS, zero external binaries**. Unpacked size is **4,653,599 bytes (~4.65 MB)**. It builds `.docx` files programmatically (a declarative document-construction API: paragraphs, tables, styles, images, page breaks) and runs identically in Node or the browser. As with react-pdf, using it for Markdown conversion means mapping the Markdown AST into its API rather than feeding it raw text — but the runtime footprint and dependency risk are about as low as this problem gets.

## 4. Vercel serverless limits (official docs, `vercel.com/docs/functions/limitations`, last updated 2026-07-01)

| Limit | Hobby | Pro / Enterprise |
|---|---|---|
| Max duration (default & max) | 300s (5 min), fixed | 300s default, **800s max** (GA), **1800s (30 min) extended max** (beta, requires per-function config, incompatible with values >800s on Secure Compute/Static IPs) |
| Memory | 2 GB / 1 vCPU (fixed) | 2 GB default, up to **4 GB / 2 vCPU** |
| Bundle size (uncompressed) | 250 MB standard (500 MB for Python) | Same, or up to **5 GB** via beta "Large Functions" (needs Fluid Compute + Active CPU, opt-in env var, not compatible with Secure Compute/Static IPs) |
| Request/response body size | **4.5 MB** max payload (`FUNCTION_PAYLOAD_TOO_LARGE` beyond that) | same |
| Concurrency | auto-scales to 30,000 | 30,000 (100,000+ Enterprise) |

Notably, all of these limits now assume **Fluid Compute**, which Vercel states is "enabled by default for new projects" — so a freshly scaffolded `apps/doc-converter` gets these numbers without extra configuration. For genuinely long-running/async workloads beyond a single invocation's duration cap, Vercel's own docs point to **Vercel Workflows** ("pause, resume, and maintain state for minutes to months without duration limits") rather than stretching a single function invocation — relevant only if conversion latency turns out to be a real problem, which the numbers below suggest it won't be for this use case.

The 4.5 MB request/response body cap is worth flagging for ticket 04 (abuse guardrails): a large pasted Markdown document, or a resulting PDF/DOCX returned inline in a single response, could hit this ceiling — worth either enforcing an input size cap well under 4.5 MB or returning generated files via streaming/blob storage rather than a single JSON/body response, if usage ever produces large outputs.

## Headline recommendation

**Primary approach: split-engine, pure-JS-native, synchronous.**

1. **Markdown parsing**: `unified` / `remark` / `remark-rehype` / `rehype` to get a shared `mdast`/`hast` representation — reused for both output paths, no bundling risk of its own.
2. **DOCX**: the `docx` npm package, mapping the Markdown AST into its document-building API. ~4.65 MB, zero external binaries, executes in low milliseconds. Trivially inside every Vercel limit on every plan tier.
3. **PDF**: `puppeteer-core` + `@sparticuz/chromium` (or `@sparticuz/chromium-min` if bundle headroom gets tight once the rest of the Next.js app shares the same 250 MB budget), rendering the same HTML the DOCX path derives from, via Chromium's print-to-PDF. This is the pattern Vercel's own KB guide documents and ships a template for. Chromium adds **~33–39 MB compressed** to the function bundle (well inside the 250 MB cap) and needs **≥512 MB RAM (1600 MB+ recommended)** — inside Vercel's memory limits on every tier. Cold start (Brotli decompression ~0.6–0.7s + Chromium launch) plus render time for a single Markdown document should land in the low-to-mid single-digit seconds, comfortably inside the **300s default/max duration Vercel gives even Hobby** — no multi-minute headroom needed.

**Sync vs. async**: for this ticket's actual scale — a personal content pipeline converting one document (case study, resume, pasted note) per request, not batch/bulk conversion — both the DOCX and PDF paths finish well within a single synchronous Vercel function invocation on any plan, including Hobby's fixed 300s cap. **No job-queue, polling, or Vercel Workflows pattern is needed** for the core conversion step; that's a straight answer to the "async infrastructure" open question flagged in `map.md`. Ticket 02 can design the UI as a normal request/response (upload or paste → immediate download), not an upload-then-poll flow. Ticket 04 should still cap input size and rate-limit requests — not because conversion is slow, but because the endpoint is public and both Chromium launches and large documents cost real CPU/memory time that's billed and could be abused.

**Risk and fallback**: the one real risk in this recommendation is the Chromium dependency for PDF — it's the heaviest piece (tens of MB bundled, 130 MB decompressed, a real browser process to launch per cold start) and the least under this app's own control (Chromium version pinning against `@sparticuz/chromium` releases, potential future bundle-size pressure as the rest of the Next.js app grows). If that risk materializes — bundle size gets tight, cold starts prove too slow in practice, or the dependency feels too heavy for what `map.md` scopes as "plain/default formatting, no custom branding" — the documented fallback is **`@react-pdf/renderer`** for the PDF path: pure JS (`pdfkit`-based), no browser binary at all, and given the plain-formatting requirement already decided in `map.md`, its component-based (not arbitrary-HTML) rendering model is less of a limitation here than it would be for a richly styled document. The tradeoff is upfront engineering cost (mapping the Markdown AST to react-pdf's own component tree instead of reusing the HTML pipeline) in exchange for eliminating the Chromium dependency's size and cold-start cost entirely.

**Ruled out**: the native Pandoc binary is a fine, lightweight, self-contained bundle for DOCX alone (~33 MB compressed, confirmed no dynamic dependencies) but has no realistic path to PDF — its own manual requires a separate LaTeX/wkhtmltopdf/typst engine that doesn't fit Vercel's bundle limits at any usable fidelity. pandoc-wasm confirms, in its own documentation, that it **cannot produce PDF at all** in the WASM sandbox for the same underlying reason, and at 58.6 MB unpacked offers no advantage over the 4.65 MB `docx` package even for the DOCX half. Neither is worth adopting when the JS-native split above covers both formats with smaller, better-understood dependencies.
